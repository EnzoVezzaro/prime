Scalability research:

- Scaling to 100K files:
  - Artifact size: ~5-50MB (depends on compression, representation)
  - Index size: ~5-20MB (symbol tables, inverted indexes, relationship graphs)
  - Performance: Sub-100ms retrieval for typical agent queries
  - Usefulness: Small-to-medium projects, should not require heavyweight database
  - Prime relevance: 100K files is modest target; SQLite or custom binary sufficient

- Scaling to 1M files:
  - Artifact size: ~50-200MB (compressed)
  - Index size: ~20-80MB
  - Performance: Sub-200ms retrieval; may need mmap for zero-copy
  - Usefulness: Medium-sized organizations, moderate codebase complexity
  - Prime relevance: Tested scale; RocksDB or custom binary with mmap

- Scaling to millions of symbols:
  - Artifact size: ~200MB-2GB (compressed, depends on symbol density)
  - Index size: ~80MB-500MB
  - Performance: Sub-500ms retrieval; may need chunked compression + mmap
  - Usefulness: Large codebases, monorepo subsets
  - Prime relevance: Key scalability target; stress test for Prime design

- Scaling to tens of millions of relationships:
  - Artifact size: ~1-5GB (compressed relationship graphs)
  - Index size: ~500MB-2GB
  - Performance: Multi-hop retrieval may be slower (O(log n) or O(sqrt(n)) with good index)
  - Usefulness: Deep codebase understanding, impact analysis
  - Prime relevance: Graph structure scalability; adjacency lists, CSM, Roaring bitmaps

- Monorepos:
  - Single repository containing multiple independent projects/services
  - Challenges: Artifact size large, whole-retrieval impractical, incremental updates critical
  - Strategies: Partition indexing by project/bounded context, content-addressed chunks, distributed knowledge
  - Usefulness: Monorepo is real-world test case (many industry codebases)
  - Prime relevance: Must support; may need sharding/distribution

- Generated code:
  - Code generated by build tools, code generators, template systems
  - Challenges: May be volatile (regenerated), large volume, hard to distinguish from hand-written
  - Strategies: Mark generated code, index with reduced fidelity, focus on hand-written boundaries
  - Usefulness: "Any codebase" requirement includes generated code (init-promt.md)
  - Prime relevance: Research area (knowledge deduplication, role identification)

- Vendored dependencies:
  - Third-party code copied into repository (vs. referenced via package manager)
  - Challenges: Volume, update frequency, license, divergence from upstream
  - Strategies: Index with attribution, treat as separate namespace, mark as vendored
  - Usefulness: Distinguish vendor code from project code for agent queries
  - Prime relevance: Role in codebase research (init-promt.md)

- Duplicated code:
  - Same or similar code appearing in multiple locations (copy-paste, generated variants)
  - Challenges: Index may store duplicate knowledge, waste of space
  - Strategies: Deduplication (symbol identity hashing), semantic compression (repeated patterns), mark as shared
  - Usefulness: "Smallest useful representation" goal (init-promt.md) depends on handling duplication
  - Prime relevance: Research area (knowledge deduplication, succinct graphs)

- Multi-language repositories:
  - Repository containing multiple programming languages simultaneously
  - Challenges: Different semantics, different indexer requirements, cross-language relationships
  - Strategies: Language-specific frontends producing common vocabulary, universal symbol ID space, cross-language relationship tracking
  - Usefulness: Strongest requirement (init-promt.md: "Prime can understand a repository containing many languages simultaneously")
  - Prime relevance: Core research; language-agnosticism across multiple languages

- Scaling dimensions:
  - Files: Number of source files in codebase
  - Entities: Number of symbols, types, functions, classes
  - Relationships: Number of calls, references, dependencies, data-flow edges
  - Prime relevance: Scale along at least three dimensions (init-promt.md)

- Scalability targets (from init-promt.md):
  - 5 files → 500 files → 50,000 files → 500,000 files → millions of files
  - 5-file project should not require heavyweight database
  - 5-million-entity monorepo should not require loading entire Prime artifact into memory
  - Incremental derivation, incremental invalidation, parallel analysis, partial loading, partial retrieval
  - Prime must support these capabilities

- Storage engine scalability comparison:
  - SQLite: Good to ~100K rows, file-based, simple queries
  - RocksDB: Scales to TB+, LSM tree, concurrent reads/writes, mmap-compatible
  - LMDB: Good to ~100M rows, minimal overhead, mmap-native, readers-unblocked
  - Custom binary: Optimizable for Prime workload; scalability depends on design
  - Columnar: Scales to large analytical workloads, less ideal for point navigation

- Prime scalability design recommendations:
  1. Design for incremental updates (no full re-index on change)
  2. Support partial loading (agent loads only needed knowledge chunks)
  3. Support partial retrieval (agent retrieves only needed symbols/relationships)
  4. mmap enable scaling beyond memory limits (virtual address space, lazy page loading)
  5. Chunked compression enables random access at scale (decompress independent chunks)
  6. Content addressing (hash-based) enables deduplication, distributed sharding
  7. Secondary indexes for agent query patterns (symbol lookups, relationship queries)
  8. Horizontal scaling: Shard artifact by bounded context/project for very large monorepos
  9. Benchmark against target dimensions (files, entities, relationships) from beginning (init-promt.md test early)
  10. Design_time scalability: Don't optimize prematurely; profile against target dimensions

- Reusable scalability components:
  - Incremental update algorithm (content hashing, delta computation)
  - Partial loading interface (retrieve subset of artifact by query)
  - Partial retrieval interface (retrieve subset of symbols/relationships)
  - mmap management (virtual address space, page fault handling)
  - Chunked compression (independent decompression chunks)
  - Content addressing (hash-based deduplication, identity, sharding)
  - Secondary index structures (symbol lookup, relationship queries)
  - Sharding/boundary detection (partition artifact by bounded context)

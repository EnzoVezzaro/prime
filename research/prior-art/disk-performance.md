# Disk & Filesystem Performance for Codebase Indexing: Prior Art and Benchmark Methodology

Date: 2026-08-20
Status: Research note (evidence-based; no product decisions made here)
Scope: Filesystem/I/O benchmark methodology for repository scan, derivation (initial/incremental/concurrent), query, and watcher workloads.

## Confidence legend

- **FACT** — Verified against a primary source (official docs, spec, source code, benchmark data).
- **OBSERVATION** — Directly observed in cited data; reproducible but context-dependent.
- **INFERENCE** — Deduced from cited evidence; reasoning shown.
- **HYPOTHESIS** — Proposed explanation or proposal; requires validation.
- **OPEN QUESTION** — Explicitly unknown; needs research.

## 1. Reference prior art: `disk-perf-git-and-pnpm`

Source: https://github.com/NullVoxPopuli/disk-perf-git-and-pnpm (README, init.sh, results table; accessed 2026-08-20).

### 1.1 Stated purpose

- **FACT**: The repo "aims to prove that something is wrong with APFS on macOS" and doubles as a stress test "when changing machine tooling that wants to observe fs events (such as security tooling / EDR / virus scanners / etc)." (README).

### 1.2 Workload construction

- **FACT**: It is a pnpm workspace containing ~30 scaffolded JavaScript-framework projects (`frameworks/`: angular, astro, emberjs ×2, gatsby, nextjs, nuxtjs, remix, sailsjs, solidjs, sveltekit, t3, tanstack-start, tutorial-kit, vite-* ×18, vue, vuepress). Projects are generated by `init.sh` using official scaffolding CLIs; `.git` and `node_modules` are then removed so the measured operations recreate them.
- **FACT**: Two measured operations:
  1. *Clean test*: `time ( git clean -Xfd; git clean -fd )` — mass **deletion** of tens of thousands of small files (node_modules trees).
  2. *Install test*: `time ( pnpm install )` — mass **creation** of tens of thousands of small files, mostly hard-link/reflink operations from pnpm's content-addressable store plus metadata writes.
- **FACT**: Network is excluded: dependencies are pre-warmed into the pnpm store before timing ("Fill the cache so we don't hit the network during testing").
- **INFERENCE**: This is a *metadata-operation-dominated* workload (create/delete/stat of many small files), not a throughput-dominated one — which matches Prime's dominant I/O shape (scan + derive over many source files).

### 1.3 Metrics and reporting protocol

- **FACT**: Single metric: shell-builtin `time` wall clock (`total` in zsh, `real` in bash), rounded to tenths of a second. `user`/`sys` are displayed but not recorded in the results table.
- **FACT**: Each PR row records: date, CPU model/core count, RAM (GB), Clean (s), Install (s), OS version, filesystem (incl. encryption state), disk model, and "Notable Software Changes" (Spotlight disabled, `csrutil disable`, EDR agents: Kandji, SentinelOne, Code42, Cyberhaven, Windows Defender sync/async).
- **FACT**: No repetition count, variance, cold/warm cache control, or phase breakdown is specified; results are crowd-sourced from contributor machines.

### 1.4 Headline results (from README table)

- **OBSERVATION**: Same workload, order-of-magnitude spread across filesystems on comparable NVMe hardware:
  - Linux ext4 on desktop CPUs: Clean ≈ 1.4–12.7 s, Install ≈ 4–31 s (e.g., Ryzen 9 9950X/ext4: 2.1/7.9 s; i9-14900HX/ext4: 2.1/9.1 s).
  - macOS APFS (Apple Silicon): Clean ≈ 30–71 s, Install ≈ 27–145 s across M1–M5 generations.
  - tmpfs (ramdisk): Clean ≈ 1.3–3.3 s, Install ≈ 4–10.7 s — an upper bound when the filesystem layer is removed.
- **OBSERVATION**: Same Apple hardware virtualized to Linux reaches ext4/btrfs-class numbers (M2 Max Parallels ext4: 3.2/12 s; M4 Pro UTM ext4: 2.5/16.9 s; M4 Pro OrbStack btrfs: 3.2/17.3 s; M1 Asahi btrfs: 6.9/20 s). This isolates the macOS/APFS software stack as the differentiator, not Apple NVMe hardware.
- **OBSERVATION**: Software-environment rows show large effects on APFS: one M3 Pro went 47.8/52.6 s → 32/53.3 s (Spotlight disabled) → 26.3/19.9 s (Spotlight disabled + `csrutil disable`); yet two M5-era entries report Spotlight exclusion had "negligible impact". Effect is inconsistent across macOS versions.
- **OBSERVATION**: Windows is also slow on this workload: NTFS 42–77 s; ReFS Dev Drive with Defender async scanning 100/**401 s** (install) — the worst row in the table despite folder exclusions.
- **OBSERVATION**: A deliberately CPU-throttled run (Ryzen 7640U clamped to ~550 MHz) degraded to 56/44 s from 6.8/5.9 s — demonstrating the workload is sensitive to CPU as well as I/O.
- **INFERENCE**: Wall-clock-only, single-run, crowd-sourced methodology can still surface robust, order-of-magnitude effects, but cannot attribute them (snapshot tax? VFS locking? FSEvents fan-out? EDR interception?) without instrumentation.

### 1.5 Community attribution attempts

- **FACT**: Hacker News discussion (news.ycombinator.com/item?id=45502173) attributes APFS slowness to (a) snapshot writes driven by Time Machine taxing mass file writes/deletes, and (b) inefficient handling of parallel I/O negating concurrent-tooling speedups. These are discussant claims, not verified measurements.
- **HYPOTHESIS**: APFS per-file costs under mass create/delete are dominated by copy-on-write metadata + snapshot retention + per-op syscall overhead, not raw device bandwidth. Requires controlled experiment (e.g., toggle `tmutil disablelocal`, compare with snapshots purged).
- **OPEN QUESTION**: Which specific APFS mechanism dominates (CoW metadata B-trees, snapshot refs, clone bookkeeping, fseventsd fan-out, Spotlight mds_stores)? No public controlled ablation exists.

## 2. APFS characteristics relevant to many-small-file workloads

Sources: Apple "About Apple File System" (developer.apple.com/documentation/foundation/about-apple-file-system), Apple File System Guide (archive), Apple File System Reference PDF.

- **FACT**: APFS features: per-file/directory clones (copy-on-write; copies occupy no additional space until modified), snapshots, space sharing across volumes in a container, fast directory sizing, atomic safe-save, sparse files, strong full-disk encryption (files *and* metadata), 64-bit, >9 quintillion files/volume.
- **FACT**: APFS uses a copy-on-write metadata scheme "without the write-twice overhead of journaling" and advertises "I/O coalescing".
- **FACT**: Fast directory sizing means directory recursive-size queries are O(1)-ish, but every create/delete must maintain those aggregated sizes — a plausible per-mutation cost (attribution: INFERENCE, mechanism unverified).
- **FACT**: Encryption covers metadata; all metadata writes pass through encryption on default setups. All macOS results in the reference table are "(Encrypted)" volumes.
- **OPEN QUESTION**: Quantified per-syscall cost of APFS metadata ops (create/unlink/rename/stat) vs ext4/xfs on identical hardware — no public apples-to-apples microbenchmark suite found.

## 3. Linux filesystem characteristics (ext4/xfs) for many-small-files

Sources: LWN.net Articles 550542, 606995, 546021; linux-ext4 mailing list (2011, 2013 threads incl. Dave Chinner).

- **FACT**: ext4 with `dir_index`/htree returns `readdir()` entries in **hash order**, not inode order; consequently readdir+stat workloads (`ls -l`) incur random-access patterns across the inode table. Coreutils mitigate by sorting readdir output by inode number before stat-ing (LWN 546021, 606995).
- **FACT**: The readdir+stat pattern requires ≥2 syscalls/file and each `stat()` can force filesystem I/O spread across multiple on-disk structures (LWN 606995). Kernel-side batching proposals (xstat/xgetdents, dirreadahead) were proposed but not merged; user space must batch itself.
- **FACT**: XFS guidance for multi-million-entry directories: increase directory block size to 8–16 KB (up to 64 KB for random ops) to make directory B-trees wider/shallower, trading CPU/memory for lower I/O (D. Chinner, linux-ext4 2013).
- **FACT**: ext4's single JBD2 journal thread creates inter-transaction dependency: an `fsync()` can be delayed behind other transactions and flush large amounts of unrelated dirty data (iJournaling, USENIX ATC'17 Park et al.).
- **INFERENCE**: For Prime's scan phase on ext4, sorting discovered paths by inode number before stat/read is a legitimate, evidence-backed optimization candidate; its benefit must be measured (HYPOTHESIS).

## 4. Filesystem watchers: event pressure, coalescing, limits

### 4.1 FSEvents (macOS)

Source: Apple File System Events Programming Guide (archive), FSEvents reference.

- **FACT**: Architecture: kernel code → special device → `fseventsd` daemon (filters) → persistent per-volume event database. Event granularity is **directory-level**: "something in this directory changed", not what.
- **FACT**: The daemon **coalesces** multiple notifications per directory within a short window; caller chooses minimum latency (seconds-scale parameter, e.g., 3.0 s in examples). At least one notification arrives after the last change.
- **FACT**: Under pressure, events may collapse to `kFSEventStreamEventFlagMustScanSubDirs`, requiring a **recursive rescan** of the subtree. Root deletion/move yields `RootChanged` (with `WatchRoot` flag).
- **FACT**: With `kFSEventStreamCreateFlagFileEvents` (10.7+) per-file events are delivered, but aggressive folding of rapid rename chains can produce batches that no longer reflect actual operation sequences; extended data (inode) since 10.13 helps disambiguate (developer report, StackOverflow 43638230).
- **INFERENCE**: During a pnpm-install-shaped burst, a Prime watcher on macOS must expect: directory-level floods, possible MustScanSub rescan fallbacks, and delivery latency governed by the chosen latency parameter — not instant per-file fidelity.

### 4.2 inotify (Linux)

Sources: inotify(7) man page; kernel docs (docs.kernel.org/filesystems/inotify.html); commit 9289012.

- **FACT**: Watches are **per-directory, non-recursive**; watching a tree requires one watch per directory, and adding watches for newly created subtrees races with file creation inside them (man-page caveat).
- **FACT**: Limits (per real UID): `max_user_instances` (default 128), `max_user_watches` (memory-scaled: ≤1% of addressable memory, clamped [8192, 1048576]; commit 9289012 raised default), `max_queued_events` (default 16384). Overflow drops events and emits `IN_Q_OVERFLOW`; applications must rescan to recover.
- **FACT**: Identical successive events are coalesced if unread; event count is therefore unreliable. Events carry no information about which process caused them.
- **FACT**: Watch cost modeled as `sizeof(inotify_inode_mark) + 2×sizeof(struct inode)` pinned per watched inode (kernel source comment).

### 4.3 fanotify (Linux)

Source: fanotify(7) man page.

- **FACT**: Mount-wide monitoring + optional **permission interception** (blocking reads until a userspace decision) — the mechanism behind AV/EDR on-access scanning. Create/delete/move events only since Linux 5.1. Queue limits analogous to inotify (`max_queued_events`, overflow → `FAN_Q_OVERFLOW`).
- **INFERENCE**: An EDR present during benchmarks (as in several reference-table rows) inserts synchronous interception into open/read paths; its presence must be recorded, ideally held constant, across runs.

### 4.4 Watchman (Meta)

Source: facebook.github.io/watchman (docs/install; site root).

- **FACT**: Uses FSEvents on macOS, inotify on Linux, USN on Windows; recursively watches roots; does not follow symlinks; supports since-clock queries and subscriptions.
- **FACT**: Overflow strategy: a dedicated thread drains kernel events as fast as possible; on kernel-reported overflow Watchman assumes everything changed and **re-crawls the whole tree** (spurious-change notifications instead of missed ones).
- **FACT**: Watchman waits for a root to **settle** before triggering notifications/actions, and conservatively treats files as changed when unsure (site root "Concepts").
- **INFERENCE**: Expected watcher behavior under mass churn: quiet during the burst (settle/coalesce), then either a compact change-set or a full recrawl. Prime's incremental design must tolerate both outcomes.

## 5. General filesystem-performance knowledge

### 5.1 Cold vs warm page cache

- **FACT**: Standard Linux cold-cache protocol: `sync; echo 3 | sudo tee /proc/sys/vm/drop_caches` before each timed run; warm-cache protocol: N untimed warmup runs (hyperfine `--prepare`/`--warmup`; sharkdp's fd and diskus benchmark scripts).
- **OBSERVATION**: diskus (parallel `du`) over 400K files/100K dirs: cold 1.746 s vs warm 0.500 s (~3.5×); single-threaded `du` cold 17.8 s vs warm 1.10 s (~16×). Parallelism recovers most of the cold-cache penalty for pure metadata scans.
- **OBSERVATION**: uutils coreutils added an explicit `warm_cache()` traversal to stabilize CI benchmarks because cold-first iterations created bimodal distributions and spurious regression alerts (uutils/coreutils PR #13958).
- **FACT**: macOS equivalent: `purge(8)` "approximates initial boot conditions with a cold disk buffer cache"; one practitioner found it made no measurable difference in their dupd/jdupes scans (virkki.com article) — effectiveness varies.
- **FACT**: USENIX ATC'24 (Li et al., "Revisiting Page Cache for File Scanning"): scanning workloads have low data-reuse; buffered-I/O page-cache misses allocate pages in the critical path and buffered I/O scales poorly as device bandwidth grows; paper proposes bypass/stream-managed caches.
- **INFERENCE**: For Prime, cold-vs-warm scan ratio is itself a key metric: it quantifies how much of Prime's cost is cache-resident metadata vs true device I/O, and predicts behavior after reboot or on CI runners.

### 5.2 fsync, queue depth, parallel I/O scaling

- **FACT**: Serial `fsync` latency bounds nothing: AWS gp2 measured ~4 ms/fsync serially yet 4800–16000 IOPS achievable via aggregation/parallelism; IOPS rise linearly with queue depth until the device limit, then latency climbs (Little's Law; Cartwright 2025 fio study).
- **FACT**: Modern Linux NVMe stacks reach millions of IOPS (3.4M with io_uring in ICPE'24 characterization; QD=1 read latency ≈68 µs); at high concurrency, I/O schedulers BFQ/MQ-deadline burn up to 78% of CPU cycles in lock traffic, while Kyber/none scale further (ICPE'24, SPEC Research).
- **FACT**: Per-worker fsync latency grows with worker count while aggregate bandwidth scales sublinearly (lni/fsyncperf data on NVMe/NVRAM instances).
- **FACT**: ext4 journal-commit contention degrades fsync tail latency under concurrent writers (ATC'17 iJournaling).
- **INFERENCE**: Prime's artifact-write path (serialization + durability) should treat fsync policy as a tunable benchmark dimension: batched group-commit vs per-file fsync will differ by orders of magnitude under concurrent derivation.

### 5.3 stat() storms, dentry/inode caching, open/close amplification

- **FACT**: readdir+stat doubles syscalls per file and forces scattered inode I/O cold (LWN 606995); dentry/inode caches make warm traversals cheap (diskus warm numbers above).
- **FACT**: Opening and reading a file adds open/close syscalls and page-cache population on top of stat; read amplification for tiny files is dominated by per-call overhead, not bytes (consistent with StreamCache findings that small-I/O buffered reads benefit from prefetch/aggregation).
- **INFERENCE**: A scanner that stats-only (mtime/size fingerprint) vs one that opens+reads every file will sit at very different points on the syscall-cost curve; Prime should measure both tiers separately.

### 5.4 CPU vs I/O bottleneck identification

- **FACT**: Shell `time` reports real/user/sys; `%CPU` column indicates wait-bound vs CPU-bound execution (reference repo instructs reading zsh `total`/bash `real`).
- **INFERENCE (methodology)**: Decompose any Prime run as: `real ≫ user+sys` → I/O-wait bound (filesystem/device/watcher interference); `sys` dominant → kernel-path bound (stat storms, page faults, lock contention); `user` dominant → CPU bound (parsing/analysis). Confirm with `pidstat`/`iostat`/`perf` where available.
- **FACT**: Inter-process concurrency inflates P99 latency ~4× vs intra-process concurrency at equal load (ICPE'24) — process architecture affects tail latency independent of total CPU.

## 6. PROPOSED: Prime filesystem benchmark plan (all HYPOTHESIS)

Everything in this section is a **proposal requiring validation**, consistent with Prime's no-premature-convergence constraint.

### 6.1 Benchmark matrix

| # | Workload | Definition | Primary metric |
|---|----------|-----------|----------------|
| B1 | Cold scan | readdir+stat+fingerprint over target repo, caches dropped | wall, user, sys |
| B2 | Warm scan | same, after 3 warmup traversals | wall, user, sys |
| B3 | Cold derivation | full parse→analyze→serialize from cold caches | wall + phase times |
| B4 | Warm derivation | same, warm caches | wall + phase times |
| B5 | Incremental derivation | touch N∈{1,10,100} files + emulate branch switch (500-file rename set); re-derive | wall, events seen |
| B6 | Concurrent derivation | K∈{1,2,4,8} workers partitioning the same repo | wall, P99 per-file |
| B7 | Random query | 100 lookups (search/lookup/context) against built artifact, shuffled | latency P50/P99 |
| B8 | Sequential query batch | same 100 queries in locality order (simulates agent session) | latency, total |
| B9 | Watcher response | start watcher; apply scripted churn (create/delete/rename bursts sized like B5); measure event-delivery latency and correctness (missed? recrawl?) | delivery latency P50/P99, false-negative count |

### 6.2 Phase separation (mandatory instrumentation)

Every derivation run records cumulative time in five buckets, so CPU-vs-I/O attribution is mechanical:

1. **scan** — directory walk + stat/fingerprint (syscall-heavy)
2. **read** — file content read (page-cache dependent)
3. **parse** — Tree-sitter parsing (CPU)
4. **semantic analysis** — symbol/relation resolution (CPU)
5. **serialize** — artifact encode + write (+ optional fsync tier)
6. **retrieve** — query-side mmap/lookup time (B7/B8)

Report `real/user/sys` alongside bucket sums; bucket-sum ≪ real ⇒ unattributed wait (filesystem, watcher, EDR).

### 6.3 Scale targets

- **S1**: 10K files / ~1M LOC (large OSS library) — expected laptop-comfortable.
- **S2**: 100K files / ~10M LOC (monorepo slice or synthetic concat) — expected to separate designs.
- **S3 (stretch)**: 500K+ files incl. a node_modules-shaped burst corpus (reuse the reference repo's own workspace as a ready-made churn generator — it is MIT-visible and reproducible via `init.sh`).

### 6.4 Platform matrix

- **P1**: macOS + APFS (encrypted, default settings) — primary dev platform.
- **P2**: Linux + ext4 (defaults) — CI baseline.
- **P3 (optional)**: tmpfs/dev/shm — filesystem-independent upper bound, mirroring the reference repo's ramdisk rows.
- Record per run: OS version, kernel, FS + encryption, disk model, CPU/RAM, power state (no throttling), EDR/AV presence, Spotlight/Indexing status, Time Machine status. Adopt the reference repo's tabular reporting format verbatim — it proved sufficient to surface order-of-magnitude effects.

### 6.5 Protocol rules

1. Repetitions: ≥5 timed runs per cell; report median + min/max (crowd-source single runs are for triage, not conclusions).
2. Cold cells: `sync; echo 3 > /proc/sys/vm/drop_caches` (Linux) or `purge` (macOS, with skepticism — verify effect once); never mix cold and warm runs in one series.
3. Warm cells: 3 untimed warmups; verify distribution is no longer bimodal (uutils lesson).
4. Quiesce before measuring: pause Spotlight indexing on target paths (`mdutil`/privacy exclusion), quit Time Machine backups during the run, document any EDR; keep these settings constant across compared cells.
5. Fixed versions: pin prime-rs commit, Tree-sitter grammars, OS point release; embed environment JSON in every result file.
6. Watcher tests use monotonic-scripted churn (deterministic file sets) so delivery-latency percentiles are comparable across platforms.
7. Never compare across virtualization boundaries (OrbStack/UTM/Parallels share host disk differently) — mark VM rows as non-comparable, as the reference table implicitly does.

### 6.6 Known pitfalls checklist

- **Page-cache pollution between phases**: a warm derivation preceded by a cold scan is neither cold nor warm; reset or pre-warm explicitly per phase.
- **Spotlight/`mds_stores` interference**: inconsistent in the wild (helped on M3 Pro, negligible on M5 Pro rows); always exclude target dirs and record the fact.
- **Time Machine local snapshots**: suspected APFS tax on mass create/delete (HN attribution); control via `tmutil` state.
- **EDR/fanotify interception**: reference-table rows with SentinelOne/Defender vary wildly (ReFS 401 s outlier); hold constant or exclude.
- **Thermal/power throttling**: demonstrated 8× degradation in-table (550 MHz row); check CPU frequency during runs.
- **inotify watch exhaustion**: 100K-file repos exceed default-ish watch budgets on some distros; log `max_user_watches` and overflow (`IN_Q_OVERFLOW`) counts; expect Watchman-style recrawl fallbacks.
- **FSEvents MustScanSub**: treat forced rescans as a distinct outcome class, not a failure of the harness.
- **First-run allocator/JIT noise**: irrelevant to Rust mostly, but mmap page-fault storms on first artifact access belong in the cold-query cell, not warm.
- **Directory hash-order stat storms on ext4**: sort by inode before stat as an experimental variant; measure, don't assume.

## 7. What Prime should adopt

- **Adopt (HYPOTHESIS)**: The reference repo's *workload shape* — mass small-file create/delete/install over a multi-project workspace — as Prime's churn generator for B5/B9; it is realistic, reproducible, and already community-understood.
- **Adopt (HYPOTHESIS)**: Its *reporting schema* (date, CPU, RAM, OS, FS, disk, notable software) extended with repetitions, variance, and phase buckets.
- **Adopt (HYPOTHESIS)**: hyperfine-style cold/warm discipline (`drop_caches`/warmup runs) from sharkdp's fd/diskus practice, including the bimodality check.
- **Adopt (HYPOTHESIS)**: Mandatory real/user/sys + phase-bucket decomposition so every result self-reports whether it was CPU-, syscall-, or wait-bound.
- **Adopt (HYPOTHESIS)**: tmpfs as a control arm to bound filesystem contribution (the reference table's most informative rows).
- **Adopt (HYPOTHESIS)**: Watcher benchmarking that scores *correctness under overflow* (missed events, recrawl size), following Watchman's documented overflow-recrawl contract, not just latency.

## 8. What Prime should avoid

- **Avoid (INFERENCE)**: Single-run wall-clock-only conclusions — the reference repo demonstrates such numbers can reveal gross effects but cannot attribute causes; Prime needs attribution.
- **Avoid (INFERENCE)**: Comparing native vs VM/containerized filesystems as if equivalent (OrbStack/UTM rows are labeled separately there for good reason).
- **Avoid (INFERENCE)**: Treating watcher event streams as complete or ordered under burst — FSEvents coalescing/MustScanSub and inotify overflow/coalescing are documented; Prime's incremental logic must be rescan-tolerant by design.
- **Avoid (HYPOTHESIS)**: Optimizing scan order or fsync policy before the matrix exists — both have evidence-backed upside (inode-sort, group commit) but unmeasured magnitude on Prime's actual artifact pipeline.
- **Avoid (FACT-driven caution)**: Drawing conclusions about "APFS is broken" style absolutes from this workload alone; the repo's own data shows environment knobs (EDR, Spotlight, snapshots, throttling) move results more than hardware generation does.

## 9. Open questions

1. **OPEN QUESTION**: What is the dominant mechanism behind APFS's mass-create/delete cost — CoW metadata B-trees, snapshot retention, clone bookkeeping, fseventsd fan-out, or userspace (pnpm/git) behavior? Needs a controlled ablation on one machine.
2. **OPEN QUESTION**: Does `purge(8)` reliably produce cold-cache conditions on modern macOS, or must Prime rely on file-set rotation (reading a larger set than RAM) for cold scans?
3. **OPEN QUESTION**: What watcher-event delivery-latency percentile should Prime target for "agent-feels-instant" incremental updates (sub-second? sub-200 ms?) — depends on agent-loop research, not filesystem research alone.
4. **OPEN QUESTION**: How much of Prime's derivation on typical repos is scan/read I/O vs parse/analyze CPU at 10K vs 100K scale? (This is precisely what B1–B6 exist to answer.)
5. **OPEN QUESTION**: Do inode-sorted scans measurably help Prime's walker on ext4, and is there an APFS-equivalent ordering trick?
6. **OPEN QUESTION**: What is the real-world frequency of FSEvents `MustScanSub` rescans and inotify overflows during ordinary developer activity (branch switches, installs) on repos of Prime's target sizes?
